## 1. Fixture, canonicalization and receipts

[envelope.json](envelope.json) is one complete synthetic Gmail **initial** envelope with two distinct records. Its account is `partheanon-interop@example.test` (a reserved synthetic identity, not a real Google mailbox). The batch ID is synthetically chosen in the accepted wire format, not claimed to be generated by the saved worker's identity algorithm. No body/snippet/attachment/link fields were added. Two records make the array-order test meaningful; Unicode in the subject checks UTF-8 hashing.

Expected base `receiptDigest`:

```text
faac0587c06150404e43c5db632378a6178fb6da539d181f3dfb57c8c358e852
```

[canonicalize.mjs](canonicalize.mjs) copies the deployed canonicalJson/ingestFingerprintInput functions exactly and adds the receiver-equivalent Web Crypto SHA-256 calculation. Hash the **original JSON envelope after successful strict validation, before account/date/display normalization**, excluding only top-level generatedAt. Sort object keys recursively using JavaScript's default key sort; preserve arrays and string values, including opaque version strings. Hash the canonical string's UTF-8 bytes, output lowercase hexadecimal. No newline is appended. This is the application's algorithm, not a claim of RFC 8785 conformance. Do not hash pretty-printed JSON, the normalized display object, the sender's reduced identity hash or the surrounding n8n item wrapper.

| --- | --- | --- |
| [Exact base](envelope.json) | faac0587c06150404e43c5db632378a6178fb6da539d181f3dfb57c8c358e852 | HTTP 200 duplicate |
| [Recursive object-key reorder](object-keys-reordered.json) | faac0587c06150404e43c5db632378a6178fb6da539d181f3dfb57c8c358e852 | HTTP 200 duplicate |
| [Top-level generatedAt changed](generated-at-changed.json) | faac0587c06150404e43c5db632378a6178fb6da539d181f3dfb57c8c358e852 | HTTP 200 duplicate |
| [records array reversed](array-reordered.json) | 0e47306e2d630fc46422be9476299fd79215cda148c6c945d4777dcd38eab8db | HTTP 409 batch_id_reused |
| [Stable subject changed](stable-value-changed.json) | 845460e6f10532a0bda97b7409b795f46a22ccbc6807b64e4a0a2a973a50b6e8 | HTTP 409 batch_id_reused |

All vectors intentionally use the same batch ID. Conflict tests must follow a successful base delivery in the same owned stream; a different account/resource/container may select a different stream. [vectors.json](vectors.json) is machine-readable. [canonical-envelope.txt](canonical-envelope.txt) contains the exact canonical bytes without a trailing newline.

Full receipt examples: [accepted](accepted.example.json), [GET lookup](lookup.example.json), [duplicate POST](duplicate.example.json). They are illustrative receiver-shaped JSON, **not captured hosted responses**. receivedAt is synthetic. The expected values assume a fresh stream: applied=2, unchanged=0, stale=0, deferred=0, sequence=1, published=true, baseline=additive, absencePruning=disabled, coverage=provisional. A real run supplies its own receivedAt. Lookup returns the original **accepted** receipt, not a new lookup status. Duplicate changes only status to duplicate and preserves the original receivedAt/sequence/counts/digest. Those original counts must not be added to operational totals again on replay.

[deferred-removal.json](deferred-removal.json) is an additional complete incremental request with a new batch ID and one null-version source deletion of the first fixture item. Expected: accepted with applied=0, deferred=1, sequence=2 after a single fresh base, both original emails remain visible, one deferred item is recorded. Its receiptDigest must be calculated from that envelope; it is not the base digest. Compatible retries do not duplicate evidence. Other ten v1.1 resource/removal examples remain available in [the branch-coverage fixtures](https://github.com/RobBrown7/Partheanon/tree/353fd1f8788016933ffec3a051bc65fbf6009463/scripts/tests/fixtures/n8n-v11).

Offline verification (Node 22+; no requests or secrets):

```sh
node docs/integrations/interop-v1.1/verify.mjs
node docs/integrations/interop-v1.1/verify.mjs --receiver
```

The second command runs within this repository with its installed dependencies and checks production helper/schema parity. The first runs with only this pack and Node. Both independently compare Web Crypto and Node SHA-256 with the immutable expected vectors. From a downloaded standalone folder, run `node verify.mjs`.

In n8n, the assistant can paste the pure functions without export declarations into a Code node operating on the **durably saved pending envelope**. If Web Crypto is unavailable there, pass their canonical string into Crypto → Hash, type SHA256, binary off, encoding HEX. Keep that internal canonical/digest field outside the POST body. HTTP must send the saved envelope only. [Official Crypto node settings](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.crypto/#hash-parameters).

Account/ID/scope/text changes change the digest. If a unique alternative synthetic identity is needed, update every account/recordKey consistently, choose a fresh logical batch ID and recalculate expectations; do not compare the personalized body with this fixed digest. Regenerating only generatedAt is compatible, but timestamp validation still applies. Do not rebuild uncertain pending deliveries from a fresh source read or sort record arrays during replay.

## 3. Hosted pilot acceptance checklist — future supervised run

Every item is **not yet performed on the hosted intake**. Keep schedules off and mock state unchanged. Before beginning, Aegis must finish persistent pending-envelope storage, destination-specific cursor/idempotency namespaces, receipt/digest validation, payload/count reporting, limits, identical replay and one-run-at-a-time enforcement. Agree that accepted includes durably deferred evidence. Operator authorization for an actual pilot is a separate step; this coordination request does not initiate it.

Record only nonsensitive evidence: execution ID/time, destination/environment, synthetic account/resource/container, batch ID, logical digest, HTTP status/content type, receipt counts/sequence, owner-side row counts and disposition. No secrets or real payloads in screenshots/logs. Pending storage must retain the minimal logical envelope and digest before the first send, and survive a sender restart. Key rotation/changes of URL must not reset or reuse a mock cursor.

- [ ] Authentication: no Site credential → hosting denial/login response, never a successful intake acknowledgment. Valid Site credential plus bad/missing application key → JSON 401. Valid credential plus another account/container in an otherwise internally consistent envelope (including its recordKeys and per-record identities) → 403. Do not follow login redirects or advance any cursor. Before the base send, scoped receipt lookup returns 404; that means no committed receipt was found, not proof an in-flight POST failed.
- [ ] Fresh baseline: deliver envelope.json only, using its matching identity/key/headers. Require HTTP 200/201/202, JSON ok=true, matching batchId, status accepted, and the expected logical receiptDigest. For a fresh receiver stream require applied=2, deferred=0, unchanged=0, stale=0, published=true, sequence=1 and provisional coverage. Do not count additive acceptance as authoritative deletion permission.
- [ ] Owner readback: in signed-in Connections, see the synthetic account's stream and matching receipt, with provisional coverage. Inbox review shows exactly two synthetic emails for this new account, including the literal `<review>` and café text, with no automatically fetched content/links. Owner-authenticated `/api/state` should expose `sources["account:<connection UUID>:gmail"]` with the same two IDs and syncTransport n8n. The service credential alone cannot call owner browser APIs. Refresh/reopen and verify persistence; never accept an HTTP response as proof of display alone.
- [ ] Receipt lookup: GET the exact batchId with the two credentials. Require the original accepted receipt, same digest/receivedAt/sequence/counts; it contains no raw envelope or secrets. A different allowed-but-unrelated container credential must not read this receipt. Recheck the original receipt after another batch: it must remain the original snapshot.
- [ ] Identical/compatible replay: exact base, recursive key reorder, and top-level generatedAt-only change → HTTP 200 duplicate and original digest/counts/sequence/time. No extra rows or deferred evidence. Sender operational totals must count this logical batch once.
- [ ] Conflicting reuse: array-reordered and stable-value-changed vectors under the same base batchId → HTTP 409 batch_id_reused. Rows and original receipt remain unchanged. Keep the pending conflict flagged; never “fix” this by silently inventing a new batch ID and advancing a cursor.
- [ ] Deferred removal: deliver deferred-removal.json under its own ID. Require accepted, applied=0/deferred=1, one persistent review entry and both emails still visible. Lookup must show that same deferred result; retry duplicate must not add another review entry. This proves conservative acceptance, not completed source deletion. Repeat Calendar null-version/occurrence cases separately using the existing resource fixtures and appropriately scoped synthetic mapping/key before claiming Calendar delivery is verified.
- [ ] Uncertain response/restart: use the manual pilot's test harness to withhold or discard a POST acknowledgment and restart the sender after its pending envelope is durable. Recover with the saved batchId and saved canonical digest. A matching committed lookup resolves it without another logical delivery. If lookup is 404/timeout, hold the cursor and retry the **saved identical logical envelope** with backoff; a matching accepted/duplicate then resolves uncertainty. Mismatched digest/ID/status or lookup 409 stays unresolved. Do not claim network interruption was tested if the harness merely discarded an already-read response; label that as a sender lost-ack simulation.
- [ ] Limits and invalid input: invalid schema/count/mode/identity → 422/no successful receipt; oversized UTF-8 body → 413. Reduce scan scope rather than truncate or split an authoritative envelope. Retry 429 using Retry-After, and uncertain 5xx/network failures through receipt lookup/identical replay, never cursor advancement on bare HTTP success.
- [ ] Sender single-flight: demonstrate the durable lock/lease for this destination stream prevents overlapping source runs; receiver CAS is not a source-run lock. Force overlapping triggers and show only one source execution owns cursor/pending-batch commits. A workflow execution setting alone must be checked against parent/worker/manual paths.
- [ ] Cursor safety: after matching receipt and parent ownership validation, commit the cursor exactly once in the **real-pilot destination namespace**. Verify mock cursors/receipts and source schedules are unchanged. Negative, conflicting and uncertain outcomes never advance it.
- [ ] Cleanup/report: capture safe receipt/digest/count evidence first. Revoke only the disposable key; once evidence is agreed, remove only the disposable connection (which clears its intake state/receipts). No real account rows are cleared. Production uses a separate restricted real-account credential and fresh bounded initial baseline. Production scheduling is a deliberate later activation, not a side effect of passing synthetic tests.

## 4. Receiver-side blockers versus live verification

**No identified receiver runtime code change is required for this bounded conservative pilot.** The existing implementation supports the fixture digest, both authentication layers, additive baseline, typed/deferred effects, durable receipt lookup and compatible replay. This pack verifies behavior without changing deployed receiver code. Credentials/mapping are not provisioned by this preparation, and actual saved-worker delivery/readback/restart recovery remain unverified.

| Item | Required action / owner |
| --- | --- |
| Secure Site-token transfer and account/key creation | Controlled owner provisioning, not a receiver code change; the current UI lacks a Site-token copy path and direct n8n credential writer |
| POST/lookup/readback, digest parity, header survival through hosting | Supervised live verification with newly prepared n8n sender |
| Persistent pending work, isolated destination cursors, count reporting, single-flight | Remaining sender implementation owned by Aegis/n8n; receiver CAS does not replace it |
| Automatic application of null-version deletions/cancellations | Not supported. Supply trustworthy source-ordering evidence (e.g. actual Gmail history version where available) or design an audited resolution/barrier protocol. Adding manual apply/retain controls or new protocol support requires receiver code; do not substitute generatedAt |
| Deferred-review disposition/retention at production scale | Current receiver shows evidence but has no apply-pending/dismiss workflow or automatic retention purge. A bounded pilot can retain evidence; unattended production needs a deliberate capacity/retention/resolution plan and may require code |
| Absence-based pruning / legacy deduplication | Intentionally disabled/unmapped, not a pilot blocker. Automation needs an agreed snapshot/barrier and explicit ownership migration, boundary/timezone rules, and receiver changes. Keep legacy rows visible and coverage provisional meanwhile |

In particular, the current sender's Gmail explicit history-deletion markers have null versions, so those deletions remain deferred. A successful pilot must not be described as fully automatic deletion synchronization or unconditional production readiness. Initial and reconcile remain additive and no rule authorizes provider writes.
